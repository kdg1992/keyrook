# Builds, dependency review and releases

## Verification

Run `./gradlew check` with JDK 25 (`.\gradlew.bat check` on Windows). The root task runs core and desktop tests, an offscreen Compose render, source-header/whitespace lint and runtime dependency checks that keep test tools out of the application. The desktop test JVM explicitly enables native access for Skiko and uses headless software rendering. This lightweight lint is not a full Kotlin style or semantic analyzer; CodeQL provides separate security analysis.

Desktop native dependency locks are stored separately for Windows x64 and Linux/macOS x64/ARM64 under `app/gradle/dependency-locks/`. Normal builds select the host platform. To review another target's dependency graph without executing its natives, run `./gradlew :app:dependencies -Pkeyrook.target=linux-x64 --write-locks` (substitute the target). This is dependency resolution, not a cross-platform runtime test.

Every resolved configuration is locked: core (`core/gradle.lockfile`), each desktop target, the root plugin classpath (`buildscript-gradle.lockfile`), settings (`settings-gradle.lockfile`) and the `build-logic` included build that holds the shared task types and conventions. After changing the version catalog, a plugin or a dependency, run `scripts/relock.sh` (extra arguments are passed to Gradle) to regenerate all of them, including all five desktop targets, then review the lockfile diff like any dependency change. It needs network access to Maven Central, the Gradle Plugin Portal and Google Maven. Lockfiles are generated, never edited by hand.

`gradle.properties` enables the local build cache, parallel project execution and the configuration cache. Task actions take their inputs from declared task properties rather than from the project at execution time, so configuration-cache problems fail the build instead of being ignored.

The `CI` workflow runs on pull requests, pushes to `main` and manual dispatch. Its stable build checks are `build-linux`, `build-windows` and `build-macos`. Each full build validates the Gradle wrapper and uses Temurin 25. Only changes entirely confined to Markdown, excluding `CHANGELOG.md`, skip expensive Windows/macOS steps. Those jobs still complete successfully; Linux runs verification. Renames are treated as deletion plus addition so a source-file deletion cannot be hidden by renaming it to Markdown. Failed path classification fails all three build checks. The classification lives in `scripts/classify-changes.mjs` and is shared with CodeQL and Dependency review. Superseded pull request runs are canceled; runs for pushes to `main`, which write the Gradle cache, always finish. Each platform job runs `check` and `:app:desktopWindowCheck` in a single Gradle invocation.

`pr-title` is its own `PR title` workflow and checks Conventional Commits using the title as data, never as shell code. Editing a title or description reruns only this check, not the platform builds. Its manual dispatch takes the title as an input so PRs that start no workflows can still be validated. Tests are not disabled to accommodate CI failures. Reports are uploaded on failure and expire after seven days.

Full platform jobs also run `:app:desktopWindowCheck` on the runner's desktop
(an isolated Xvfb display on Linux). It creates native AWT window peers without
showing them, checks internal-dialog transitions, external-focus and minimization
event routing under each window lock choice, then verifies listener/window
disposal. Events are controlled test inputs; this is not proof of actual
operating-system lock/sleep notification delivery. The task refuses local
execution so it cannot interact with a user's working desktop. Ordinary tests additionally exercise real Toolkit dispatch and
the Swing inactivity timer without native windows.

CodeQL uses the stable 2.27.1 bundle explicitly because the action's default 2.27.0 extractor does not support Kotlin 2.4.20. Review this bundle pin alongside Kotlin and CodeQL action updates. On documentation-only pull requests (the CI classification) the `CodeQL` job skips setup, compilation and analysis and completes successfully; the source is identical to the analyzed base, and no empty result is uploaded that could close alerts. Pushes to `main`, the weekly schedule and manual dispatches always analyze.

## Dependency graph and review

`dependency-submission.yml` resolves all Gradle dependencies on `main` without a full build and submits the graph. It also accepts a manual dispatch on the Release Please branch, whose PR otherwise has no graph for Dependency review. Runtime classpaths are marked as runtime; test and build-tool dependencies remain in the graph as development dependencies.

For a PR, `dependency-submission-pr.yml` generates a graph with read-only repository permissions and uploads it as a seven-day artifact. `dependency-submission-upload.yml` runs only after that named workflow succeeds. It uses the pinned Gradle action to retrieve the triggering run's artifacts and submit them. This privileged job has no checkout, Gradle execution, shell commands or cache restoration; it does not execute PR code. `actions: read` is needed to retrieve that other run's artifact. The PR graph workflow is not a required check, so a path filter skips it for Markdown-only changes other than `CHANGELOG.md`.

`dependency-review.yml` waits up to 15 minutes for snapshots. High/critical vulnerabilities in every scope fail the check. Licenses must be on the configured GPL-3-compatible allowlist; missing/unresolved licenses also fail. A final API check rejects remaining snapshot warnings, because the upstream action can proceed after its retry timeout. Missing graphs must never be interpreted as a clean review. Documentation-only pull requests cannot change dependencies, so the job skips the review and completes successfully; any other change without a submitted graph fails on missing snapshots. A manual dispatch reviews the dispatched branch head against `base-ref` (default: its merge base with `main`) and reports on that head commit.

The reviewed JUnit versions have narrow package/version exceptions because EPL-2.0 JUnit is separate test tooling. `checkRuntimeDependencies` enforces its absence from the runtime. There is also a single-revision exception for Gradle Actions: its repository includes both MIT code and a proprietary cache component, so GitHub cannot assign one license to the whole repository. Every workflow explicitly selects `cache-provider: basic`, the MIT implementation, and never uses enhanced caching. Updating these exceptions requires a fresh review. None of these exceptions exempts a dependency from vulnerability checks.

The Dependabot configuration schedules Monday updates for Gradle and GitHub Actions. Only minor and patch updates are grouped, so every major update (Gradle or GitHub Actions) arrives as its own PR. Bouncy Castle (`org.bouncycastle*`) and Apache MINA SSHD (`org.apache.sshd*`) stay outside the Gradle group and always arrive as separate PRs. Security-library and major-version updates require maintainer review; no workflow auto-merges dependency PRs. Gradle updates are titled `fix(deps)` so that Release Please releases runtime library updates; an update that only touches build or test tooling is retitled `build(deps)`. GitHub Actions updates use `ci(deps)` and never start a release. Dependabot updates only the core lockfile, so every Gradle update is completed with `scripts/relock.sh` for all desktop targets and, for runtime libraries, a matching update of the reviewed native inventories before it can be merged.

## Safe initial activation

This section is historical. The workflows were activated through separate reviewed pull requests: build checks first, then dependency-graph generation and its privileged uploader, then CodeQL and Dependency Review, and finally the release workflow. The uploader had to exist on the default branch before the review gate could evaluate a PR's graph. Follow the same order when bootstrapping a fork or a new repository; never bypass a failed dependency review to activate its own uploader.

## Release process

`version.txt` is the Gradle version source. Release Please uses the `simple` strategy and `.release-please-manifest.json` to maintain a release PR containing the next version and changelog. Feature commits increase the minor version, fixes the patch version and a breaking change (`!` after the type or a `BREAKING CHANGE:` footer) the major version. Until 1.0.0, the configuration also set `bump-minor-pre-major`, which turned a breaking change into a minor increase, so the 0.x releases never reached 1.0 by themselves; the final 1.0 pull request removed it together with `bump-patch-for-minor-pre-major`, because both only apply while the major version is zero.

Version 1.0.0 is produced deliberately, not by a breaking commit. When squash-merging the final 1.0 pull request (documentation and release-please configuration), the maintainer ends its description with the footer line `Release-As: 1.0.0`. Because squash merges use **PR title and description** as the commit message (see [repository settings](#repository-settings-after-the-first-green-runs)), that footer becomes the last line of the squash commit body on `main`, and Release Please then proposes exactly 1.0.0 in its next release PR. Put nothing after the footer, and do not write `Release-As:` or `BREAKING CHANGE:` lines in other PR descriptions, since every description becomes part of a commit that Release Please parses. If the setting is different, the footer is lost and Release Please proposes an ordinary 0.x version or no release at all; do not merge such a release PR, but correct the setting and land the footer in a follow-up commit.

From 1.0.0 on, Keyrook follows [Semantic Versioning](https://semver.org/) for the vault format and application behaviour (see the [compatibility promise](FORMAT.md#compatibility-promise-from-100)): `feat` raises the minor version, `fix` the patch version, and a breaking change raises the major version. Breaking changes are avoided; a breaking commit needs the owner's explicit approval before it is merged. Supported versions and the handling of bundled JDK updates are described in the [security policy](../.github/SECURITY.md#supported-versions).

Release PRs are merged only after explicit release approval and green checks. The workflow uses only `GITHUB_TOKEN`; it does not need a personal token. **PRs created or updated by that token do not run `pull_request` workflows on their own**, but `workflow_dispatch` events do. Whenever Release Please creates or updates its PR (`prs_created`), the `release-pr-checks` job calls `release-pr-checks.yml`, which needs only `actions: write` and dispatches `Dependency submission`, `CI`, `CodeQL`, `Dependency review` and `PR title` (with the PR title) on the release branch. Those runs report `build-linux`, `build-windows`, `build-macos`, `CodeQL`, `dependency-review` and `pr-title` on the branch head commit, which is the PR head; CI has no pull request base there and always runs the full build. `Recover release pull request` does the same for its replacement PR. GitHub also creates `pull_request` runs for such a PR, but because the PR was opened by the GitHub Actions bot they stop in the *action required* state until a maintainer approves them. With the required status checks of the `main` ruleset these pending runs block the merge even when the dispatched runs are green. For every release PR the maintainer therefore opens the PR and selects **Approve and run workflows**; the approved runs report the same six checks as regular pull request runs, and that approval is part of the deliberate release review. The ruleset has no bypass list, so this step cannot be skipped by anyone, the maintainer included. If a dispatch fails, run `Release PR checks` manually from `main` with the PR title. Do not accept results for an earlier commit or merge without those checks.

Once an approved release PR is merged, Release Please creates its tag and a **draft** GitHub release (`draft` and `force-tag-creation` in `release-please-config.json`), which is not public and not reported by `releases/latest`, so the application's update check cannot announce it yet. Three downstream jobs in the same workflow build Windows MSI, macOS DMG and Linux DEB/RPM packages using `release_created` and `tag_name`. They have read-only permissions. The `installer-tests` matrix job then downloads each platform's packages from the same run and installs, upgrades from the previous published release where one exists, runs the installed launcher's `--self-test`, and removes them: DEB on the Ubuntu runner, RPM in a digest-pinned Fedora container, the per-user MSI silently on the Windows runner and the DMG bundle into a temporary Applications directory on macOS. It needs only `contents: read` and `actions: read` (for the run artifact), uses `GITHUB_TOKEN` alone and uploads Windows Installer logs only on failure, for seven days. See [Installer tests](PACKAGING.md#installer-tests) for exactly what is and is not covered. After all builds and installer tests succeed, an isolated publishing job, the only downstream job with `contents: write`, verifies each platform's checksums, finds the draft by tag in the release list (the tag endpoint omits drafts), uploads all four installer formats, legal notices and their archives, combined `SHA256SUMS.txt`, and unsigned-installation instructions, and only then publishes the draft as the latest release. It does not rely on another workflow being triggered by the tag. If packaging or an installer test fails, the release stays an unpublished draft: rerun the failed jobs for a transient failure, or discard the draft and its tag and replace it through `Recover release pull request` as described in [Native packaging](PACKAGING.md#when-packaging-or-installer-tests-fail).

Manually dispatching `Release` runs the three-platform packaging matrix and the installer tests without creating a tag or release and retains successful verification outputs for seven days. Native jobs have a 40-minute limit. Packaging and installer-test jobs use explicit runner images (`ubuntu-24.04`, `windows-2025`, `macos-15`) rather than `*-latest`, so an image migration never silently changes installers; move them deliberately and rerun the manual release. The actual runner architecture determines each package target, so a replacement image must keep x64 (Linux, Windows) or ARM64 (macOS). The inventory is independent of the image: it covers the resolved runtime artifacts and the hash-pinned packaging JDK. The inventory is collected and uploaded in its own Gradle invocation; its verification, tests and packaging share the next one. Packages are built only in GitHub Actions; local native builds are refused.

Reviewed native-library and bundled-JDK inventories exist for Windows x64, Linux x64 and macOS ARM64. The mandatory `checkNativeDistributionLicenses` task compares them with exact hashes of the resolved runtime artifacts and JDK legal files and fails before jlink/jpackage when a record is absent or stale. See [Native packaging](PACKAGING.md) for the inventory format, unsigned-installation guidance and release failure handling. A complete manual run and installation tests must succeed before the first installer release is approved. No signing certificates or paid services are configured.

## Repository settings after the first green runs

These settings are not changed by repository files. An administrator must inspect and apply them after the corresponding checks exist:

- **Settings → General → Pull Requests:** enable only squash merging, use PR title and description for the commit message, and enable automatic head-branch deletion.
- **Settings → Actions → General → Workflow permissions:** default to read-only contents and allow Actions to create pull requests. No custom secrets are required.
- **Settings → Rules → Rulesets → main:** require a PR, an up-to-date branch and `build-linux`, `build-windows`, `build-macos`, `pr-title`, `dependency-review` and `CodeQL`; prohibit force-pushes and branch deletion. Confirm exact check contexts from real runs before saving. Keep the bypass list empty; release PRs are unblocked by approving their `pull_request` runs (see [Release process](#release-process)).
- **Settings → Code security:** enable Dependabot alerts and security updates, and confirm Secret Scanning is enabled. Verify Gradle dependencies in the graph rather than assuming the version catalog alone populates it.

All runners are standard GitHub-hosted runners. Actions use full commit SHAs, minimal job permissions and timeouts. Public workflow logs/artifacts must contain only synthetic test data. Caches on PRs are read-only. Release runs and CI runs for `main` are never canceled by a newer run.
